# Архитектура и приватность

## Компоненты

```
┌──────────────┐   WebSocket /ws (JSON)   ┌──────────────────────────────┐
│  Приложение  │ ───────────────────────▶ │ Сервер                       │
│  (Expo)      │                          │  • Hub — присутствие в памяти │
│  профиль,    │ ◀─────────────────────── │  • пересылка E2E-сообщений   │
│  чаты, ключи │   peers, dm, zone, map   │  • REST кабинета             │
│  — локально  │                          │  • SQLite: только заведения  │
└──────────────┘                          └──────────────▲───────────────┘
                                                         │ REST /api/cabinet
                                              ┌──────────┴─────────┐
                                              │ Кабинет заведения  │
                                              │ (React, /cabinet/) │
                                              └────────────────────┘
```

| Данные | Где живут | Сколько |
|---|---|---|
| ключи устройства (Ed25519 + X25519) | Keychain / Keystore телефона (`expo-secure-store`) | пока не сброшены |
| профиль, фото, настройки, блокировки | AsyncStorage телефона | пока пользователь не удалит |
| переписка | AsyncStorage телефона, до 500 сообщений на чат | пока пользователь не удалит |
| профиль на сервере | память процесса | пока открыто соединение |
| сообщения на сервере | нигде (пересылаются сразу) | — |
| огрублённая позиция (режим «карта») | память процесса | 30 минут или до отключения |
| заведения, их сети и события, аккаунты владельцев | SQLite | постоянно |

## Зона = одна сеть

`shared/src/net.ts → networkKeyFromIp`:

* IPv4 публичный → сам адрес; IPv4-mapped IPv6 сводится к IPv4;
* IPv6 → префикс /64 (устройства одной сети получают адреса из одного /64);
* частный IPv4 (10/8, 172.16/12, 192.168/16, 100.64/10, 169.254/16) → подсеть /24 —
  на случай, когда сервер стоит в той же локальной сети.

Клиент присылает `net.type` и `hashSsid(SSID)` (SHA-512 с контекстом, первые 16 байт). Правило видимости в зоне
(`Hub.canSeeInZone`):

```
ключи сети равны
и (SSID неизвестен хотя бы у одного или хэши равны)
и оба не в режиме «невидимка»
и никто никого не заблокировал
```

`net.type = cellular` → клиент попадает в зону из одного себя: CGNAT оператора объединяет случайных людей.

За реверс-прокси обязательно `TRUST_PROXY`, иначе сервер увидит адрес прокси у всех клиентов.

### Заведение в зоне

Сеть заведения = `(network_key, ssid_hash | NULL)`. Пара уникальна, одна сеть принадлежит одному заведению.
Приоритет совпадения: точный SSID → сеть без SSID → гость без SSID. После любых изменений в кабинете хаб
пересчитывает заведение для подключённых гостей и шлёт `zone` (`Hub.refreshVenues`).

## Рукопожатие и идентичность

1. Сервер шлёт случайный `challenge`.
2. Клиент отвечает `hello`, в котором:
   * `id` — публичный Ed25519-ключ устройства;
   * `boxPk` — X25519-ключ для сообщений;
   * `keySig = sign("ryadom/boxkey/v1|" + boxPk)`;
   * `sig = sign("ryadom/hello/v1|" + challenge)`.
3. Сервер проверяет обе подписи, иначе закрывает соединение (код 4002). Повторное подключение с тем же `id`
   вытесняет старое (4001).

Клиенты тоже проверяют `keySig` у каждого собеседника, поэтому сервер не может подменить ключ шифрования,
не подменив саму личность. Подмену личности ловит «код безопасности» в чате (`safetyCode`): его сверяют при встрече.

## Личные сообщения

`nacl.box` (X25519 + XSalsa20-Poly1305), шифрует и расшифровывает только клиент. Сервер пересылает `{nonce, box}`
и отвечает отправителю `dm_status`: `delivered` / `offline` / `forbidden`. Если адресат заблокировал отправителя,
сервер отвечает `offline`, чтобы не раскрывать блокировку.

Кому можно писать (`Hub.canMessage`):

* человеку, которого видишь в зоне или на карте;
* тому, кто написал тебе первым (до перезапуска сервера);
* **взаимному контакту**: когда оба написали друг другу, клиенты сообщают серверу `contact`, а при каждом
  подключении присылают локальный список контактов. Переписка продолжается из любой сети и переживает
  перезапуск сервера, но сервер не хранит граф контактов — его подтверждают оба устройства.

## Карта

* Режим `map` включает только сам пользователь (вкладка «Я» или кнопка на карте).
* Координаты огрубляются на телефоне до центра ячейки фиксированной сетки (1 км или 250 м,
  `coarsenLocation`). Сервер огрубляет повторно и точных координат не видит. Сетка фиксированная,
  поэтому усреднение повторных запросов ничего не даёт.
* Позиция живёт 30 минут без обновления, при отключении удаляется.
* Взаимность (`MAP_RECIPROCAL=true`): людей на карте видит только тот, кто сам на ней.
  Заведения и события — публичный REST `/api/venues?bbox=…`.
* В выдаче карты нет фото и возраста — только ник, эмодзи-аватар, цели и статус. Полный профиль отдаётся
  по `get_profile`, если человек виден запрашивающему.

## Защита от злоупотреблений

* zod-валидация каждого сообщения; лимит кадра 256 КБ, фото в профиле ≤ 120 000 символов (≈ 90 КБ).
* Ведро токенов на соединение (30 запросов залпом, 3 в секунду; тяжёлые операции дороже). После 50 нарушений
  соединение закрывается.
* Жалоба засчитывается, только если жалующийся действительно видел человека. N разных жалоб за 24 часа
  (`REPORT_THRESHOLD`) дают бан идентичности на `BAN_HOURS`. Известное ограничение: новая идентичность
  генерируется бесплатно. Дальше понадобятся лимиты по сети и аттестация устройства.
* Пароли владельцев заведений хранятся как scrypt (N=16384) с солью. В базе лежат только SHA-256 токенов сессий.
  Попытки входа ограничены по IP и e-mail.
* Статистика для заведения k-анонимна: числа видны от `MIN_GROUP` человек, по каждой цели тоже.

## Что сервер может и чего не может

| Может | Не может |
|---|---|
| видеть, какие ключи подключены из какой сети и когда (в памяти) | прочитать сообщения |
| видеть публичные профили людей, пока они онлайн | подменить ключ шифрования собеседника незаметно |
| видеть огрублённую позицию тех, кто включил карту | узнать точные координаты или название Wi‑Fi |
| знать, кто кому пишет, пока сообщения идут | восстановить переписку после доставки |

## Масштабирование (дальше)

Хаб — один процесс. Для горизонтального масштабирования: шардирование по `network_key` (вся зона на одном инстансе),
пересылка личных сообщений и карты между инстансами через Redis pub/sub, геоиндекс (geohash) вместо линейного
прохода по карте.
